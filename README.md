# Online Learning Project

## Описание

Проект Online Learning Project представляет собой бэкенд-приложение для системы онлайн-обучения с кастомной авторизацией по Email и полноценным REST API для управления курсами, уроками, подписками и приёмом онлайн-платежей.  
Проект контейнеризирован с помощью Docker и Docker Compose, а также автоматизирован для непрерывной интеграции и доставки (CI/CD).

## Технологии

*   **Backend:** Python / Django / Django REST Framework (DRF)
*   **Database:** PostgreSQL (хранение данных и истории отправок)
*   **Dependencies:** Poetry (управление пакетами и виртуальным окружением)
*   **Контейнеризация:** Docker / Docker Compose (сетевая изоляция сервисов)
*   **WSGI-сервер:** Gunicorn (многопоточный production-сервер для Django)
*   **Прокси-сервер:** Nginx (раздача статики/медиа и проксирование запросов к Gunicorn)
*   **CI/CD Автоматизация:** GitHub Actions (автоматическое тестирование, проверка линтером и деплой)

## Схема оркестрации контейнеров (Docker Compose)

Вся архитектура проекта онлайн-обучения разбита на 6 изолированных контейнеров, общающихся во внутренней сети Docker:
* `django_postgres` — СУБД PostgreSQL 16 (порт скрыт внутри сети).
* `django_redis` — Хранилище Redis (кэш и брокер сообщений для Celery).
* `django_celery` — Асинхронный воркер для событийных рассылок писем через SMTP Яндекс.
* `django_celery_beat` — Планировщик периодических задач (еженощная блокировка неактивных пользователей).
* `django_web_app` — Веб-приложение Django REST Framework, запущенное через Gunicorn на порту 8000.
* `django_nginx` — Веб-сервер Nginx, который слушает стандартный **порт 80** для внешнего интернета, проксирует запросы к Django и самостоятельно раздает файлы из общих томов `django_static` и `django_media`.

## Инструкция по запуску проекта

### 1. Подготовка окружения
Убедитесь, что у вас установлена платформа Docker. 

Создайте файл **`.env`** в корневой директории проекта и заполните его вашими параметрами по следующему шаблону:

```
SECRET_KEY="ваш_секретный_ключ_django"
DEBUG=True

# Настройки PostgreSQL (В качестве HOST обязательно указываем имя сервиса 'db')
DB_NAME=online_learning
DB_USER=postgres
DB_PASSWORD=your_secure_password
DB_HOST=db
DB_PORT=5432

# Технические переменные для инициализации контейнера Postgres
POSTGRES_DB=online_learning
POSTGRES_USER=postgres
POSTGRES_PASSWORD=your_secure_password

# Настройки Redis и Celery (В качестве HOST указываем имя сервиса 'redis')
REDIS_URL=redis://redis:6379/1

# Интеграции (Stripe / Email)
EMAIL_HOST=smtp.yandex.ru
EMAIL_PORT=465
EMAIL_HOST_USER=your_email@yandex.ru
EMAIL_HOST_PASSWORD=your_app_password
STRIPE_SECRET_KEY="sk_test_..."
```
*Важно: Если в вашем `SECRET_KEY` используется знак доллара (`$`), продублируйте его (`$$`), чтобы избежать ошибок парсинга со стороны Docker Compose.*

### 2. Запуск всех сервисов единой командой
Запустите сборку образов и поднятие контейнеров (Django, PostgreSQL, Redis, Celery Worker, Celery Beat) в фоновом режиме:
```
docker compose up -d --build
```

### 3. Первичная инициализация приложения
После успешного запуска контейнеров выполните команды миграции, сбора статики и создания администратора:

* **Применить миграции базы данных:**
  ```
  docker compose exec web python manage.py migrate
  ```
* **Собрать статические файлы (CSS/JS) для админ-панели:**
  ```
  docker compose exec web python manage.py collectstatic --noinput
  ```
* **Создать суперпользователя (администратора):**
  ```
  docker compose exec web python manage.py createsuperuser
  ```

## Интеграция эквайринга Stripe

В систему интегрирована возможность онлайн-оплаты курсов через **Stripe API**.

### Ключевые особенности реализации:
1. Вся логика взаимодействия со Stripe вынесена из контроллеров в сервисный модуль (`services.py`). Функции общаются с внешним API и возвращают структурированные JSON-словари.
2. Секретные ключи (`STRIPE_SECRET_KEY`) инициализируются на стороне бэкенда.
3. Расширена существующая модель `Payments` в приложении `users`. Добавлен новый способ оплаты (`stripe`), поля для сохранения ID сессии, ссылки на оплату и статуса транзакции (`open` / `complete` / `expired`).
4. Реализован эндпоинт для проверки транзакций. Сервер обращается к Stripe API, верифицирует факт списания виртуальных денег и обновляет статус в локальной базе данных проекта.

## Архитектура эндпоинтов оплаты (Приложение `users`)

Все финансовые эндпоинты требуют обязательной JWT-авторизации (передачи токена в заголовке `Authorization: Bearer <token>`).

### 1. Инициализация покупки и генерация ссылки
* **URL:** `/users/payments/`
* **Метод:** `POST`
* **Тело запроса (JSON):**
  ```json
  {
      "paid_course": 2
  }
  ```
* **Логика работы:** Контроллер динамически подтягивает цену из модели `Course`, после чего последовательно вызывает три обязательных этапа Stripe API:
  1. `stripe.products.create` — Регистрация курса как продукта.
  2. `stripe.prices.create` — Создание цены.
  3. `stripe.checkout.sessions.create` — Генерация платежной сессии Checkout.
* **Успешный ответ (`201 Created`):**
  ```json
  {
      "id": 5,
      "paid_course": 2,
      "payment_amount": "5000.00",
      "payment_type": "stripe",
      "payment_link": "https://stripe.com_...",
      "status": "open",
      "created_at": "2026-07-01T00:19:40.790813+03:00"
  }
  ```

### 2. Просмотр истории платежей текущего пользователя
* **URL:** `/users/payments/`
* **Метод:** `GET`
* **Поддерживаемый функционал:** Постраничная пагинация, фильтрация по полям `paid_course`, `paid_lesson`, `payment_type`, а также сортировка по дате создания (`ordering=-created_at`).

### 3. Проверка и синхронизация статуса платежа
* **URL:** `/users/payments/status/<int:pk>/`
* **Метод:** `GET`
* **Логика работы:** Контроллер извлекает сохраненный `session_id`, делает запрос к эндпоинту `stripe.checkout.sessions.retrieve`, перезаписывает статус в локальной БД и отдает развернутый отчет:
  ```json
  {
      "payment_id": 5,
      "course": "Основы Django REST Framework",
      "amount": "5000.00",
      "stripe_status": "complete",
      "payment_status": "paid"
  }
  ```

## Основные эндпоинты API (Маршруты)

### Пользователи (`/users/`)
* `GET /users/profile/<id>/` — Просмотр профиля пользователя (включает полную историю его платежей, информацию об оплаченных курсах и уроках).
* `PATCH /users/profile/<id>/` — Частичное редактирование профиля (город, телефон, аватар).
* `GET /users/payments/` — Просмотр списка всех платежей в системе (доступна фильтрация и сортировка).

### Курсы и Уроки (`/learnings/`)
* `GET /learnings/courses/` — Получить список всех курсов (с вложенными уроками и общим количеством уроков через `SerializerMethodField`).
* `POST /learnings/courses/` — Создать новый курс.
* `GET /learnings/lessons/` — Получить список всех уроков.
* `POST /learnings/lessons/create/` — Создать новый урок (требуется передать `course` id).
* `PATCH /learnings/lessons/update/<id>/` — Редактировать урок.
* `DELETE /learnings/lessons/delete/<id>/` — Удалить урок.

### Фильтрация и Сортировка

Для списка платежей (`/users/payments/`) подключен `django-filter` и настроена фильтрация по связанным объектам (через их первичные ключи `id`), а также сортировка.

**Доступные параметры фильтрации:**
* По курсу: `?paid_course=<id>`
* По уроку: `?paid_lesson=<id>`
* По способу оплаты: `?payment_type=cash` (или `transfer`)

**Доступные параметры сортировки:**
* По дате оплаты (от старых к новым): `?ordering=payment_date`
* По дате оплаты (от новых к старым): `?ordering=-payment_date`

### Ролевая модель и управление правами доступа (DRF Permissions)
В проекте реализовано разграничение прав доступа между типами пользователей на основе кастомных классов прав (`DRF Permissions`), встроенных механизмов аутентификации и групп Django.

### Подписки (APIView)
* `POST /learnings/subscribe/` — Управление подпиской. 
  **Тело запроса (JSON):**
  ```json
  {
      "course": 2
  }
  ```
  *При первом запросе подписка создается (ответ: `"Подписка добавлена"`), при повторном — удаляется (ответ: `"Подписка удалена"`).*

**Натройка ролей в проекте:**

1. **Обычный пользователь** — имеет доступ только к собственному учебному контенту и своему профилю. Может просматривать только общую инфо о других пользователях.
2. **Модератор** — пользователь, состоящий в группе `moderators` (назначается через панель администратора). Обладает расширенными правами на просмотр и редактирование, но ограничен в управлении контентом (не может добавлять/удалять уроки и курсы).
3. **Администратор (Суперпользователь)** — полный доступ ко всем функциям системы и удалению аккаунтов.

### В проект были интегрированы следующие ключевые возможности
1. **Система подписок на курсы (`APIView`):**
   - Реализован эндпоинт-переключатель для подписки/отписки авторизованных пользователей на обновления конкретных курсов.
   - В сериализатор курса добавлено динамическое вычисляемое поле `is_subscribed`, отображающее статус подписки текущего пользователя.

2. **Валидация контента (`Validators`):**
   - Создан кастомный класс-валидатор `YoutubeOnlyValidator`.
   - Запрещено добавление любых сторонних ссылок (в поле видео уроков и текстовые описания курсов/уроков), кроме `youtube.com`.

3. **Пагинация (`Pagination`):**
   - Настроен постраничный вывод списков в файле `paginators.py`.
   - Для курсов установлено ограничение в 5 элементов на страницу (`CoursePagination`), для уроков — 10 элементов (`LessonPagination`).
   - Поддерживается динамическое изменение размера страницы клиентом через query-параметр `?page_size=`.

4. **Полное покрытие тестами (`APITestCase`):**
   - Написаны комплексные тесты для всех имеющихся эндпоинтов (CRUD курсов, CRUD уроков, логика подписок, валидация и разграничение прав доступа для модераторов).

## Интеграция фоновых и периодических задач (Celery & Celery-Beat)

В проект интегрирована система асинхронного выполнения задач и периодического планирования на базе **Celery** и **Celery-Beat**. В качестве брокера сообщений и бэкенда результатов используется **Redis**.

### Ключевые особенности реализации:
1. **Безопасность конфигурации:** Все параметры подключения к брокеру вынесены в переменные окружения (`.env`) и не попадают в открытый репозиторий.
2. **Синхронизация временных зон:** Настройки времени Django (`TIME_ZONE = 'Europe/Moscow'`) и планировщика Celery (`CELERY_TIMEZONE`) строго синхронизированы. Дополнительно активирован параметр `CELERY_ENABLE_UTC = False`, что гарантирует запуск периодических задач точно по локальному времени бэкенда.
3. **Оптимизация запросов к БД:** Фоновые задачи спроектированы с использованием методов массового обновления ORM (`.update()`).

## Бизнес-логика асинхронных задач

### 1. Событийная рассылка уведомлений об обновлении курсов
* **Задача:** `learnings.tasks.send_course_update_emails`
* **Триггер:** Автоматически вызывается методом `perform_update` в контроллерах при изменении курса или любого связанного с ним урока.
* **Логика и ограничения:** 
  * Задача выполняется асинхронно через метод `.delay()` и не блокирует основной HTTP-поток API.
  * Реализовано ограничение по времени: уведомление отправляется подписчикам только в том случае, если данный курс не обновлялся последние 4 часа.
  * Письма отправляются через настроенный SMTP-шлюз (в режиме разработки подключен `console.EmailBackend`).

### 2. Периодическая автоматическая блокировка неактивных пользователей
* **Задача:** `users.tasks.block_inactive_users`
* **Триггер:** Запускается автоматически планировщиком `Celery-Beat` по расписанию.
* **Логика работы:** 
  * Задача анализирует БД и находит пользователей, у которых флаг `is_active=True`, но дата последнего входа (`last_login`) составляет более 30 дней назад от текущего момента.
  * Из выборки исключаются суперпользователи (`is_superuser=False`).
  * Найденным неактивным пользователям массово проставляется флаг `is_active=False`, блокируя им доступ к LMS.
* **Расписание (План):** В файле `settings.py` задача зафиксирована в блоке `CELERY_BEAT_SCHEDULE` на ежедневный запуск строго в полночь (`crontab(hour=0, minute=0)`).

## Сценарий интерактивного тестирования блокировки

1. Переведите планировщик в тестовый 30-секундный режим, раскомментировав блок `test_block_inactive_users_every_30_seconds` в файле `config/settings.py`.
2. Запустите все три терминала (Django, Worker, Beat).
3. Перейдите в панель администратора Django по адресу и откройте раздел кастомных пользователей.
4. Выберите любого активного тестового пользователя (не админа), перейдите в блок «Важные даты» и вручную измените поле «Последний вход» (Last login), установив дату на пару месяцев назад от текущего дня. Сохраните изменения.
5. В терминале 2 (Worker): в течение 30 секунд воркер перехватит задачу от Beat, зафиксирует изменения в БД и выведет лог об успешной блокировке 1 пользователя.
6. Обновите страницу общего списка пользователей в админке — зелёный маркер активности у данного пользователя сменится на красный крестик блокировки.
